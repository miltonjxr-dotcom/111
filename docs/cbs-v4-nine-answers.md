## 问题一：B 类未解锁状态下的做空对冲

### 1.1 场景

B1 机构供给方（如 VC）持有大量未解锁 Token。虽然 Token 被锁定不能卖出，但它可以在衍生品市场做空来**锁定当前利润**——如果价格下跌，空头获利弥补未解锁 Token 的账面损失；如果价格上涨，空头亏损但未解锁 Token 增值。净效果是"提前套现"。

### 1.2 是否可监测

| 路径 | 可行性 | 说明 |
|------|:------:|------|
| **链上 Perp 做空（Hyperliquid/GMX）** | ✓ 可监测 | 如果 B1 用已知地址在链上 Perp 开空仓，完全可追踪。这就是 Perp 修正项的核心场景之一 |
| **CEX Perp 做空** | ✗ 不可监测 | CEX 内部交易完全不透明。只能通过间接信号推测（如从链上提出 USDT 到 CEX → 可能是做空保证金） |
| **OTC 远期/期权对冲** | ✗ 不可监测 | 完全链下，没有链上痕迹 |
| **通过关联地址操作** | 部分可能 | 如果 VC 用非标记地址做空，理论上不可追踪。但 Entity Resolver 可能通过 Gas Funder 分析发现关联 |

### 1.3 结论

**链上 Perp 做空可以监测且已纳入 Perp 修正项；CEX 和 OTC 对冲只能推测。** 实事求是地说，大部分 VC 的对冲操作发生在 CEX 或 OTC 市场，链上可见比例可能不到 20%。但 Hyperliquid 的崛起正在改变这个比例——越来越多机构在链上 Perp 操作。

**系统处理方式**：
1. B 类实体的链上 Perp 空头仓位 → 纳入 Perp 修正项（已有设计）
2. B 类实体从链上提出大额 USDT/USDC 到 CEX → 在指标 6 事件流中标记"可能为做空保证金"（推测性标签，置信度低）
3. 不做无法验证的推测

## 问题二：做市商之间的筹码转移

### 2.1 场景分析

Token 从做市商 A 转移到做市商 B，可能原因：

| 可能原因 | 概率 | 投研含义 |
|---------|:----:|---------|
| 项目方更换做市商 | 中 | 可能对原做市商不满（服务质量/费用/利益冲突） |
| 新增一家做市商（原做市商不撤） | 高 | 可能为上所做准备或增加流动性 |
| 做市商间的 OTC 交易 | 中 | 做市商之间的大宗交易，可能反映某方的方向性判断 |
| 做市商的做市基金更换（如子基金轮换） | 低 | 内部运营变化，中性 |

### 2.2 客观评价

**这确实值得监测，但信号是模糊的。** 你说得对，"项目方对做市商不满"只是推测之一，不能作为确定性结论。

**是否算异常？** 算。做市商之间的大额 Token 转移本身就是非常规事件，满足指标 6"偏离基线"的定义。但这个事件的方向性（看多还是看空）不确定：
- 如果是更换为更知名的做市商 → 可能偏正面
- 如果原做市商被"开除" → 可能暗示项目存在问题
- 如果是增加做市商 → 偏正面

### 2.3 处理方式

纳入指标 6 层 2（事件流），标记为"做市商变更"事件，**不计入层 1 量化评分**（因为方向性不明确）。由人类分析师判断具体含义。

```
事件类型: C1_TRANSFER (做市商间筹码转移)
方向性: 不确定
处理: 指标 6 层 2 事件流 (不计入层 1 评分)
推送优先级: 中 (需分析师判断)
展示信息:
  - 来源做市商 / 目标做市商
  - 转移金额 / 占总做市量比例
  - 来源做市商是否同时在撤 LP (如果是→偏负面)
  - 目标做市商是否在增加 LP (如果是→偏正面)
```

## 问题三：E1 借贷——"避免清算=仍看好"是否成立

### 3.1 客观分析

**不一定成立。** 追加抵押物避免清算的原因不只是"看好"：

| 追加抵押物的原因 | 是否代表"看好" | 概率 |
|---------------|:--:|:----:|
| 仍然看好该 Token 的长期价值 | 是 | 中 |
| 不想被强制清算（税务原因、不想在低点实现亏损） | 否 | 中高 |
| 清算会导致更大的连锁反应（如 DeFi 协议财库） | 否 | 低 |
| 习惯性操作（机械式加保证金） | 否 | 中 |
| 买时间——先避免清算，等找到更好的退出时机 | 不一定 | 中 |

### 3.2 更准确的信号解读

```
旧解读: 避免清算 = 仍看好 (过度简化)

修正后:
  追加抵押物 → "该实体选择不在当前价格被迫出局"
                ≠ "该实体看好"
                = "该实体认为当前价格清算的代价 > 追加保证金的代价"
                → 有一定参考价值，但置信度不高
                → 标注为: LIQUIDATION_AVOIDED (信号置信度 0.3)

  大额追加 (追加量 >> 维持线) → 更有意义
    说明该实体不仅仅是"勉强续命"，而是主动增加缓冲
    → 信号置信度提升至 0.5

  接近清算但不追加 → 更强的信号
    说明该实体可能已经放弃或准备被清算
    → 风险预警信号
```

### 3.3 总结

**"避免清算=仍看好"作为大方向不完全错，但过于粗糙。** 修正为"追加抵押物=选择不在当前价格被迫出局"，作为低置信度的参考信号。真正有价值的是"追加幅度"和"是否接近清算但不追加"这两个衍生信号。

## 问题四：A 层主标签是否完备 + 实现路径

### 4.1 完备性检查

| 标签 | 是否可覆盖 Web3 绝大多数获利模式 |
|------|-----|
| 事件驱动型 | ✓ 在事件前布局 |
| 趋势配置型 | ✓ 顺势中长线 |
| 早期发现型 | ✓ Token 极早期介入 |
| 均值回归型 | ✓ 逆向操作 |
| 供需博弈型 | ✓ 利用解锁/做市等供给信息 |
| 叙事轮动型 | ✓ 跟随热点板块轮动 |
| 被动配置型 | ✓ 类指数基金 |
| **缺失：高频/量化型** | 高频套利、统计套利等量化策略 |
| **缺失：生态建设型** | 以 LP/质押为核心获利手段而非方向性交易 |

### 4.2 是否需要补充

**高频/量化型**：大部分应该已被 D1（MEV/套利/Bot）过滤。但有些量化基金的策略不完全是噪音（如动量策略），其链上行为可能有参考价值。**建议：暂不补充，V1 中如遇到不可归类的实体标为"未分类"。**

**生态建设型**：确实存在一类实体主要通过做 LP、质押、流动性挖矿获利，而非方向性交易。**建议：补充为 P2 标签，V1 不实现。**

### 4.3 实现路径

```
Phase 0 (人工):
  对白名单中最重要的 200-500 个实体，由投研团队手动标注 A 层标签
  依据: Arkham/Nansen 已有标签 + 链上交易历史人工分析
  产出: 种子标签数据集

Phase 1 (半自动):
  基于积累的交易数据，自动计算 P0 标签 (3个):
  
  事件驱动型:
    条件 = 实体在 ECS 标记的事件前 72h 建仓次数 / 总建仓次数 > 30%
    数据需求 = ECS 事件日历 + 实体交易记录
    
  趋势配置型:
    条件 = 平均持仓周期 > 14 天 且 建仓时价格 > 20日均线 的比例 > 50%
    数据需求 = 交易记录 + 价格数据
    
  早期发现型:
    条件 = 买入时 Token 流通市值 < $10M 或 上线 < 30天 的比例 > 40%
    数据需求 = 交易记录 + Token 市值/上线时间
  
  其他实体 → "未分类"
  人工复核: 自动标注结果由投研团队抽样验证

Phase 2 (全自动):
  扩展到 P1 标签 + 全白名单覆盖
  引入 ML 分类器，用 Phase 0/1 的人工标注数据作为训练集
```

## 问题五：数值参数的确定逻辑

### 5.1 "72h"等参数为什么选这个值

这些参数不是随意选的，但也不是已经验证的最优值。它们是**合理的初始假设，需要回测验证后调优**。以下是每个参数的选择逻辑和调优方案：

| 参数 | 当前值 | 选择逻辑 | 调优方式 |
|------|--------|---------|---------|
| 事件驱动判定窗口 | 72h | 重大事件公布前，内幕信息泄露到行为体现通常在 1-3 天内。太短（12h）会漏掉提前布局者；太长（7d）会混入正常交易噪音 | 回测：用历史事件前 24h/48h/72h/96h/168h 分别统计聪明钱建仓率，找信号最强的窗口 |
| 趋势配置持仓周期 | >14 天 | 区分"配置"和"短线"的经验阈值。<3 天=日内，3-14 天=波段，>14 天=配置 | 回测：不同持仓周期区间的实体的后续胜率分布 |
| 早期发现市值阈值 | <$10M | 低于 $10M 通常是极早期、尚未被广泛关注的项目 | 可调为 $5M/$20M/$50M，根据不同市场周期有不同合理值 |
| 买入确认推定时间窗口 | 24-72h | CEX 出入金到链上操作的典型间隔。太短会漏掉正常操作延迟；太长会产生过多误匹配 | 统计历史已知买入案例的 CEX→链上时间间隔分布 |
| 异常规模阈值 | 3 倍中位数 | 统计学中 >3σ 通常被视为异常。这里用 3 倍中位数作为简化版 | 回测不同倍数（2x/3x/5x）下的信号准确率 |
| Perp 对冲折扣阶梯 | 0.9-0.35 | 梯度设计确保轻度对冲仅轻微折扣，重度对冲大幅折扣 | Phase 3 通过回测优化具体阶梯 |
| 持仓集中度分层阈值 | 0.1%/0.01% | 参考传统金融的大股东认定（>5%/1%），缩小比例适应 crypto 更分散的持仓 | 可针对不同市值 Token 动态调整 |
| 标签衰减周期 | 30d/-10% | 30 天不活跃开始降权，是"月度活跃"概念的体现 | 统计不同衰减速度下的标签预测准确率 |

### 5.2 核心原则

**V1 阶段所有参数都是"合理初始值"，不是"验证后最优值"。** Phase 3 的信号回测框架的核心任务之一就是验证和优化这些参数。

建议在文档中统一标注：
- `[DEFAULT]` = 初始默认值，基于经验假设
- `[TUNABLE]` = 可调参数，Phase 3 通过回测优化
- `[FIXED]` = 固定逻辑，不需要调优

## 问题六：买入路径不止 CEX——DEX 链间对价也算

### 6.1 你说得对

v3.1 的买入路径 #3 只写了"CEX 等额对价推定买入"，但实际上非 CEX 的场景也存在：

| 路径 | 示例 |
|------|------|
| 地址从 ETH 链转入主要资产到 Aster DEX → 后转出 Aster Token 到 BSC | 跨链 DEX 对价买入 |
| 地址通过 Thorchain 从 BTC 链直接 swap 为某 ERC20 Token | 跨链原子交换 |
| 地址通过 LayerZero OFT 将 Token 从链 A 转到链 B 后在 B 链卖出 | 跨链后操作 |

### 6.2 修正

将买入路径 #3 从"CEX 等额对价推定"扩展为**"交易场所等额对价推定"**：

```
修正前:
  #3: CEX 等额对价推定买入

修正后:
  #3: 交易场所等额对价推定买入
    a) 向 CEX 转入主要资产 → 后从 CEX 提出风险 Token
    b) 向 DEX 专属链/侧链转入主要资产 → 后转出该 DEX 原生 Token
       (如 Aster: ETH→Aster链 → 后 Aster Token→BSC)
    c) 通过跨链 DEX 协议直接兑换 (Thorchain, Chainflip 等)
    d) 通过 OTC desk 链上地址对价转移

  识别方式:
    - 检测白名单地址在时间窗口内:
      (1) 向已知交易场所转出主要资产
      (2) 从同一或关联交易场所接收风险 Token
      (3) 金额大致匹配 (±20% 容差，考虑手续费和滑点)
    
  置信度: 0.6-0.8 (取决于金额匹配度和时间窗口)
```

## 问题七：卖出是否也应有 7 个子项

### 7.1 分析

买入有 7 个路径，卖出不完全对称：

| 买入路径 | 对称的卖出路径 | 是否存在 |
|---------|-------------|:------:|
| #1 DEX Swap 买入 | DEX Swap 卖出 | ✓ |
| #2 聚合器路由买入 | 聚合器路由卖出 | ✓ |
| #3 交易场所对价推定买入 | 交易场所对价推定卖出 | ✓ |
| #4 LP 隐含买入（区间穿越） | LP 隐含卖出（区间穿越） | ✓ |
| #5 LP 意图买入（区间设定） | LP 意图卖出（区间设定） | ✓ |
| #6 跨链后买入 | 跨链后卖出 | ✓ |
| #7 OTC 对价买入 | OTC 对价卖出 | ✓ |

**结论：确实应该是 7 个。** v3.1 只写了 5 个是不完整的。卖出的 7 个子项与买入完全对称，方向相反。

## 问题八：Event Layer 举例 + 双触发模式

### 8.1 Event Layer 每步举例

**场景：Uniswap V3 上发生了一笔 Swap 事件**

```
原始事件: 
  Chain: Ethereum
  Block: 19234567
  Tx: 0xabc...
  Event: Swap (Uniswap V3 Pool: USDC/TOKEN_X)
  From: 0x7a25...3f8b
  Amount0: -50,000 USDC (流出)
  Amount1: +125,000 TOKEN_X (流入)

Step 1 — 原始事件接收:
  解析出: 地址 0x7a25 用 50,000 USDC 换了 125,000 TOKEN_X

Step 2 — D类地址过滤:
  查询 D 类黑名单: 0x7a25 不在 D1/D2/D3/D4 名单中
  检查行为模式: 非 Sandwich 模式 (前后 block 无反向交易)
  → 通过，继续

Step 3 — 结构行为穿透:
  检查 tx 的调用栈: msg.sender = 0x7a25 (EOA 直接调用)
  不是 Router/Bridge/Solver/闪电贷
  → 无需穿透，继续

Step 4 — 白名单匹配:
  查询白名单: 0x7a25 = "A3 匿名高质量买方"，实体 ID: SM_0042
  → 命中白名单，进入精细分析

Step 5 — 行为分类:
  事件类型: Swap
  方向: USDC(主要资产) → TOKEN_X(风险资产) = 买入
  确认级别: 绝对确认 (同 hash 内主要资产减少 + 风险资产增加)
  → 分类: 真实买入

Step 6 — 标准化事件输出:
  {
    entity: "SM_0042",
    entity_class: "A3",
    token: "TOKEN_X",
    action: "CONFIRMED_BUY",
    amount_usd: 50000,
    confidence: 1.0,
    chain: "ethereum",
    timestamp: "2026-04-14T10:23:45Z",
    tx: "0xabc...",
    labels: []
  }
  → 计入: 指标 1 (+$50K), 指标 3 (如果是首次参与则 +1 实体)
```

**场景：白名单地址向 Binance 转入大额 Token**

```
原始事件:
  Event: Transfer
  From: 0xdef...（已标记为 Paradigm 关联地址）
  To: 0x28c...（已标记为 Binance 充值地址）
  Token: ETH, Amount: 2,000 ETH (~$5M)

Step 1: 解析出 Paradigm 向 Binance 转入 $5M ETH
Step 2: 0xdef 不在 D 类 → 通过
Step 3: 直接 Transfer，无需穿透
Step 4: 0xdef = Paradigm (A1 机构买方) → 命中白名单
Step 5: Transfer to 已知 CEX = 迁移行为 (CEX 入金)
  注意: 入 CEX ≠ 已卖出，只是迁移
Step 6: 输出:
  {
    entity: "Paradigm",
    entity_class: "A1",
    token: "ETH",
    action: "CEX_DEPOSIT",
    amount_usd: 5000000,
    confidence: 1.0,
    chain: "ethereum",
    destination: "Binance",
    labels: ["LARGE_TRANSFER"]
  }
  → 计入: 指标 4 (CEX 入金 +$5M), 指标 6 (层 1 偏空评分 + 层 2 事件推送)
  → 不计入指标 1 (不是确认卖出)
```

### 8.2 双触发模式

#### 模式 A：白名单扫描触发（主动发现）

```
触发源: 系统定时扫描白名单内实体地址

流程:
  每小时批处理:
    遍历白名单全部地址 → 拉取最新链上事件
    → Event Layer 处理 → 输出标准化事件
    → 指标计算引擎更新 7 个指标
    → CBS Score 更新
    → 如果触发异动条件 → 推送

  适用场景: 日常监控，发现白名单实体的所有异动
  
  优点: 不遗漏任何白名单行为
  缺点: 不能发现非白名单地址的异常行为
```

#### 模式 B：跨模块触发（被动响应）

```
触发源: 其他模块检测到某 Token 异动，通知 CBS 进行扫描

流程:
  MTS/NDS/ECS/BAS → 检测到 $TOKEN_Y 的异动信号
  → 通知 CBS: "请检查 $TOKEN_Y 的资金行为"
  
  CBS 收到请求后执行两步:
  
  Step 1 — 白名单维度扫描:
    查询白名单中所有持有/近期交互过 $TOKEN_Y 的实体
    → 检查近期是否有异常行为
    → 如果有 → 生成事件，更新指标
    → 如果没有 → 标注"白名单无异动"（本身也是信号——其他模块看到异动但聪明钱没动，可能是噪音）
  
  Step 2 — Token 维度扫描 (非白名单):
    拉取 $TOKEN_Y 近期的全量大额交易/LP 变化/持仓变化
    → 识别是否有"疑似高质量但不在白名单"的地址在大额操作
    → 如果发现 → 标记为"待入库观察地址"（可能是新的聪明钱）
    → 同时更新指标 5 (持仓集中度) 和指标 7 (流动性动态)，这两个指标本身不限白名单

  优点: 能发现非白名单地址的异常行为 + 白名单不动本身也是信号
  缺点: 依赖其他模块触发，有延迟
```

#### 两种模式的关系

```
模式 A (白名单扫描) = 常驻运行，每小时批处理
  → 发现"聪明钱在做什么"
  → 可能触发对某 Token 的深度关注

模式 B (跨模块触发) = 按需运行，其他模块通知时执行
  → 回答"这个 Token 上聪明钱有没有动"
  → 可能发现新的聪明钱地址

两者互补:
  A 发现 → "Paradigm 买了 TOKEN_Y" → 可能触发 NDS/ECS 检查 TOKEN_Y 的叙事/事件
  B 回应 → "NDS 说 TOKEN_Y 在热议" → CBS 扫描后发现"白名单无异动" → 可能是纯噪音
```

## 问题九：指标 7 深度部分与 MTS 流动性是否重叠

### 9.1 MTS 的流动性指标看什么

MTS（市场交易信号）关注的是**"市场是否已经开始交易它、拥挤它、重新定价它"**。MTS 的流动性维度看的是：
- 交易量/成交量变化
- 买卖价差（Spread）
- 订单簿深度（CEX 端）
- 滑点大小

MTS 的视角是**交易者视角**——"我要买/卖这个 Token，成本有多大？"

### 9.2 CBS 指标 7 看什么

CBS 指标 7 关注的是**"资金在流动性层面有什么异动"**：
- 池子深度变化（有人在撤/加 LP）
- 撤池行为检测
- 流动性集中度
- 流动性迁移方向

CBS 的视角是**资金行为视角**——"谁在流动性上做了什么动作？这反映了什么意图？"

### 9.3 是否重叠

| 维度 | MTS 关注 | CBS 指标 7 关注 | 重叠？ |
|------|---------|----------------|:------:|
| 池子深度 | 作为交易成本指标（"滑点多大"） | 作为资金行为指标（"有人在撤流动性吗"） | **数据相同，视角不同** |
| 交易量 | 核心关注 | 不关注 | 不重叠 |
| 买卖价差 | 核心关注 | 不关注 | 不重叠 |
| 撤池行为 | 不关注 | 核心关注 | 不重叠 |
| 流动性集中度 | 不关注 | 核心关注 | 不重叠 |
| 流动性迁移 | 不关注 | 核心关注 | 不重叠 |

**结论：有一项底层数据重叠（池子深度），但分析视角和信号含义不同。** MTS 看的是"深度够不够交易"，CBS 看的是"深度变化反映了什么资金行为"。

**建议处理**：
- CBS 指标 7 的 7a 子项（池子深度变化）侧重**变化量和变化速度**（"深度在 24h 内骤降 40%"），而非绝对值
- MTS 侧重深度的**绝对值**（"当前 2% 深度 = $500K"）
- 两者在 Dashboard 中分别展示，底层数据可共享，但指标计算独立

如果团队认为即便视角不同也不应有数据重叠，可以将 7a 从 CBS 移除，只保留 7b/7c/7d。**但这会削弱 CBS 对"流动性骤变"风险信号的捕捉能力**——撤池行为 (7b) 和深度变化 (7a) 经常是同一事件的两面，分开看信号更完整。

**建议保留 7a，但在跨模块文档中明确标注"CBS 7a 与 MTS 共享底层数据，分析视角不同"。**
